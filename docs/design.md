# 設計

## 判断

公開可能な監視エンジンを1リポジトリに集約。UIは依存のない静的HTMLにしてホスティングと保守費用を抑えます。初期対象はヤプルの公開トップページ1件。既存の私有台帳を公開リポジトリへコピーしません。将来は台帳から監視許可・所有権が確認済みのURLとIDだけを非公開実行環境へ渡す設計です。既存台帳との自動同期・共通Workflowへの抽出は未実装。

1. 管理者が設定をレビュー（最大30サイト、2デバイス、固定ホスト）。
2. PSIから4カテゴリと主要ラボ指標を取得。エラーは独立記録。
3. 新規ブラウザコンテキストで撮影。Cookie/ログイン状態を持ち込まない。
4. JSTの日付とUTC測定時刻で画像とJSONを保存。
5. 保存記録から履歴、週間集計、公開候補レポートを生成。

`records/<site-id>/YYYY-MM-DD/<device>.json` と `screenshots/<site-id>/YYYY-MM-DD/<device>.jpg`。同日再実行は既存レコードをスキップ。画像だけ保存済みなら再利用します。失敗を含めて1日1記録を保持し、自動上書き・削除・間引きはありません。途中失敗は再実行で未作成分だけ進められます。過去日付の捏造・バックフィルはしません。

JPEG品質75を採用。最大3MB/画像・高さ16,000px。WebPへの変換は実測後の改善候補。シリアル実行なので対象への負荷が小さく、最大120 PSIリクエスト/実行（通常60、429/5xx時1回だけ再試行）、60枚/実行です。30サイトの実運用試験は未完了。30分のworkflow上限に届く場合は対象数を減らしてから並列化を検討します。

## セキュリティ境界

任意URLを受け付けるSaaSではありません。信頼できる管理者が編集した設定だけを使用。トップURLはHTTPS、443、ユーザー情報・query・fragmentなし。撮影の全HTTPリクエストはGET/許可ホストのみ、DNSの全回答を検査しpublic unicastだけ許可、検査済みIPへ接続を固定してDNS rebindingを防ぎます。redirect先も同じrouteを通します。WebSocket、Service Worker、POSTをブロック。各画像は最大160リクエスト・30MB応答、各応答8MB・15秒上限。PSIはGoogle側の計測サービスへURLを渡すためGoogleの外部取得が発生します。

外部フォント・CDN等は設定に追加しない限りブロックされます。見た目が実ブラウザと異なる可能性をレポート利用者は考慮してください。許可ホストに個人情報が表示されるページを追加しないでください。メディアの自動マスキングや画像内PII検出は未実装。

共有環境での敵対的サイト実行を想定した完全なsandboxではありません。専用GitHub-hosted runnerで実行し、対象拡大・外部ユーザー受付前にはブラウザの隔離/egress firewall、所有権確認、テナント分離、秘密情報を持たない撮影workerを追加します。R2は専用bucketの最小権限キーを使用します。

## 履歴・検知

直近30回のPerformanceとLCPをSVGで描画。欠測で線を途切れさせ、表で値を参照可能。ダッシュボードでは当日未取得を警告。直近6回すべて成功し、直近3回の値がその前3回の中央値より各10点以上低い場合だけ継続低下候補とします。自動通知やIssue起票は行いません。曜日・季節性やLighthouseバージョン差の補正は未実装です。

最新の7日間について成功日数/期待7日、Performance中央値を出力。監視開始前の期間も期待7日として表示するため、開始初週は不足が表示されます。レポートには生成日時を表示。Actions自体が停止するとレポートも更新されないので、独立した監視は別途必要です。

## 公開レポートへの接続

`npm run report -- --public` の出力ディレクトリだけをレビュー後に静的サイトの `/reports/speedwatch/` などへ配置できます。`report.json` と `weekly.json` は `version: 1`。website側はこれらをビルド時に読み込み、サイトID/デバイス/日付で関連付けられます。非公開bucketへブラウザから直接アクセスさせません。実際のwebsite変更・自動デプロイはこのPRに含めません。
